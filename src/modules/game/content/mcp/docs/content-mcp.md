# Content MCP: administration and agent connections

The MCP server is part of the existing Express API. Its public connection URL is
`https://YOUR_API_HOST/api/v1/game/content/mcp`. It is disabled by default.
`src/server.ts` mounts `mcp/route/index.ts` before the app's general body parsers,
sanitizers, and CORS middleware. Models hold persistence, handlers implement domain
work, services adapt HTTP/MCP requests, and routes define the exposed endpoints.

## Enable the endpoint

Configure these variables in the API deployment, then restart its workers:

```dotenv
CONTENT_MCP_ENABLED=true
CONTENT_MCP_URL=https://api.example.com/api/v1/game/content/mcp
CONTENT_MCP_HOSTS=api.example.com
CONTENT_MCP_ORIGINS=https://api.example.com,https://approved-editor.example.com
```

These are **backend environment variables**. Set them in the API's deployment
environment (or its local `.env` when using local HTTPS). They are read at process
startup, so restart all API workers after changing them. Example domains below
are placeholders, not the project's configured domains.

| Variable | What to put here | Current behavior |
| --- | --- | --- |
| `CONTENT_MCP_ENABLED` | The literal string `true` to enable MCP; `false` or omit it to disable | Only exact lowercase `true` enables the routes. |
| `CONTENT_MCP_URL` | The full public HTTPS MCP endpoint, e.g. `https://api.example.com/api/v1/game/content/mcp` | Required when enabled. Must end at that exact path, with no trailing slash, query, fragment, or embedded credentials. Used as the OAuth resource/audience and to build discovery and OAuth URLs. |
| `CONTENT_MCP_HOSTS` | Comma-separated API hostnames, e.g. `api.example.com` | Required when enabled and must include the canonical URL's host. No scheme or path. Include a non-default port when present, e.g. `api.example.com:8443`. Validates the incoming `Host` header; this is the API host, not the admin website's host. |
| `CONTENT_MCP_ORIGINS` | Comma-separated browser origins, e.g. `https://admin.example.com,https://approved-editor.example.com` | Required when enabled. Use exact HTTPS scheme + host + optional port, with no path or trailing slash. Include the admin UI's origin. The API's canonical origin is added automatically. Applies to MCP, OAuth, and admin routes. |

For an API at `https://api.example.com` and an admin UI at
`https://admin.example.com`, a minimal configuration is:

```dotenv
CONTENT_MCP_ENABLED=true
CONTENT_MCP_URL=https://api.example.com/api/v1/game/content/mcp
CONTENT_MCP_HOSTS=api.example.com
CONTENT_MCP_ORIGINS=https://admin.example.com
```

Hosts/origins are deployment allowlists, not permission grants. An approved origin
still needs valid authentication and an explicit grant. Native or server-side
agents often omit Origin; they still need valid MCP tokens. OAuth callback URLs
are a separate per-client registration field (`redirectUris`), not an ENV value.
Allowing a browser origin does not register its callback or authorize its client.

The existing API configuration is reused:

| Existing variable | MCP relevance |
| --- | --- |
| `JWT_SECRET` | Existing app JWT signing secret, used to verify human administrators. Keep the API's existing value. MCP agent tokens are opaque and do not use this secret. |
| `REDIS_URL` | Shared Redis endpoint for limits across workers. Existing default is `redis://localhost:6379`; use the deployment's shared Redis endpoint. |
| `REDIS_TOKEN` | Optional Redis password, if your Redis deployment requires it. |
| `MONGO_USER`, `MONGO_PASS`, `CLUSTER_STRING` | Existing MongoDB SRV connection inputs. All three must be present for the current database configuration to use that connection. `CLUSTER_STRING` is the cluster hostname, without `mongodb+srv://`. |
| `MONGO_DBNAME` | Existing application database name. MCP uses its own collections in that same database. |

The current database loader builds its URI from these components; it does not
read a `MONGO_URI` environment override. Missing connection components select the
existing local `mongodb://localhost:27017/...` fallback. MCP provisioning and
writes require that connection to support transactions (replica set or sharded
cluster). A deployment already using a suitable cluster needs no separate MCP
database credentials.

Do not create an MCP client-secret ENV variable on the API: client secrets are
generated by registration/rotation endpoints and returned once. The agent stores
its issued secret in its own secret storage. No new `NEXT_PUBLIC_*` secret belongs
in the frontend. The admin app already uses `NEXT_PUBLIC_API_ORIGIN` for its public
API origin; it can derive the MCP URL by appending `/api/v1/game/content/mcp`.

The present validator requires HTTPS even for local MCP development and rejects
`http://localhost:3000` as an allowed browser origin. Use an explicitly configured
local HTTPS setup or an HTTPS development endpoint. HTTP loopback OAuth callbacks
are permitted when preregistered, but do not relax the separate Origin policy.
Token lifetimes, page/body limits, and request limits currently have code defaults;
there are no ENV overrides for them.

For copyable local ENV values, a Docker Desktop HTTPS proxy, certificate trust,
and verification commands, follow [the Windows local testing guide](./local-testing.md).

Frontend implementation details are in [the frontend handoff](./frontend-handoff.md).

Use the real public HTTPS URL. Hosts are exact `Host` values, including a port if
present; origins are exact HTTPS origins. Wildcards are rejected. The canonical
API origin is also allowed. Clients without an Origin header can connect; clients
with one must match the allowlist. Configure the HTTPS reverse proxy to preserve
the approved Host. Use the app's existing MongoDB, Redis, and `JWT_SECRET` settings.
Redis must be available across all workers; limiting failures reject requests.
MongoDB must support transactions for provisioning, token issuance, proposals,
and content mutations. A standalone instance can serve reads using already-issued
valid tokens, but rejects writes with `transactions_required`.

## Exposed routes

Let `BASE` mean `/api/v1/game/content/mcp`.

| Route | Purpose / authentication |
| --- | --- |
| `BASE` | Stateless MCP HTTP transport; MCP OAuth bearer token |
| `BASE/oauth/authorize` GET / POST | Account sign-in and consent; preregistered client + S256 PKCE |
| `BASE/oauth/token` POST | URL-encoded authorization-code, refresh-token, or client-credentials exchange |
| `BASE/oauth/revoke` POST | URL-encoded token revocation; authenticate its registered client |
| `/.well-known/oauth-protected-resource/api/v1/game/content/mcp` GET | Protected-resource discovery |
| `/.well-known/oauth-authorization-server` GET | OAuth discovery; no public registration endpoint |
| `BASE/admin/clients` GET / POST | List / preregister clients |
| `BASE/admin/clients/:clientId` PUT | Change name, exact callbacks, or active state |
| `BASE/admin/clients/:clientId/rotate-secret` POST | Replace confidential secret and revoke old tokens |
| `BASE/admin/grants` GET / POST | List / approve explicit grants |
| `BASE/admin/grants/:id` PUT | Change permissions, boundaries, expiry, or active state |
| `BASE/admin/grants/:id/revoke` POST | Revoke grant and tokens immediately |
| `BASE/admin/proposals` GET | List proposals, optionally `?state=pending` |
| `BASE/admin/proposals/:id` GET | Inspect normalized payload and rationale |
| `BASE/admin/proposals/:id/approve` POST | Apply reviewed payload after revalidation |
| `BASE/admin/proposals/:id/reject` POST | Reject without modifying content |
| `BASE/admin/audit` GET | Inspect call, denial, decision, and mutation audit records |

Admin routes require an existing human app JWT in `Authorization: Bearer ...`.
The account must currently be active and email-verified. Management requires
persisted `mcp:manage`; review requires `mcp:review`. Existing administrator roles
also qualify. Permissions are resolved from current Auth/Admin records, not roles
claimed in the JWT. Agent credentials cannot use these admin routes. Ordinary app
JWTs and internal API keys cannot authenticate the MCP transport.

Admin responses use `{ "success": true, "payload": ... }`; OAuth responses use
standard OAuth fields. List routes accept `page` and `limit` (maximum 50).
Every administrative mutation requires a fresh `operationId`, as do agent writes.

## Issue access to an unattended agent

An administrator issues a **client credential and a separate grant**. Creating a
client alone gives it no platform access. No admin frontend is included in v1;
use these backend endpoints from an authenticated administrative API client.

1. POST `BASE/admin/clients` with the human administrator JWT:

   ```json
   {
     "operationId": "register-library-agent-001",
     "clientId": "library-agent",
     "name": "Library authoring agent",
     "kind": "machine",
     "confidential": true,
     "redirectUris": []
   }
   ```

   Save `payload.clientId` and `payload.clientSecret` securely. The random secret
   appears only in the first successful response. Storage and audit contain no
   plaintext secret; an identical retry returns metadata without the secret.
   If the response is lost, rotate the secret with a **new** operation ID.

2. POST `BASE/admin/grants` with the same human JWT:

   ```json
   {
     "operationId": "grant-library-agent-001",
     "clientId": "library-agent",
     "ownerId": "REPLACE_WITH_ACTIVE_VERIFIED_AUTH_RECORD_ID",
     "capabilities": ["read", "propose"],
     "contentTypes": ["items", "skills", "abilities", "settings", "lore", "combatants"],
     "settingKeys": ["REPLACE_WITH_EXISTING_SETTING_KEY"],
     "shared": false,
     "expiresAt": "REPLACE_WITH_FUTURE_ISO_8601_UTC_DATETIME"
   }
   ```

   `ownerId` is the existing account's 24-character MongoDB Auth ID, not its profile
   ID or email. The expiry is mandatory. Save the returned grant `_id` for
   management and revocation. A machine client has one grant and an accountable
   owner; deactivating or unverifying that owner disables its access.

3. Give the agent only its client ID, client secret, and MCP URL. The agent POSTs
   `BASE/oauth/token` as `application/x-www-form-urlencoded`:

   ```text
   grant_type=client_credentials
   client_id=library-agent
   client_secret=THE_ONE_TIME_SECRET
   resource=https://api.example.com/api/v1/game/content/mcp
   scope=read propose
   ```

   The response contains `access_token`, `token_type: Bearer`, and `expires_in`
   (15 minutes). Use that access token in MCP requests. Obtain another token when
   it expires. Machine grants do not issue refresh tokens. Confidential clients
   may alternatively authenticate using HTTP Basic.

To grant direct writes, PUT `BASE/admin/grants/:id` with an operation ID and the
complete desired capability list, for example `read`, `propose`, `create`,
`update`, `bulk`, `read:draft`. Publishing additionally requires `publish`.
Existing tokens retain their original scope ceiling; request a new token for
new capabilities. Restrictions and revocations take effect on current tokens.

To revoke, POST `BASE/admin/grants/:id/revoke` with
`{ "operationId": "revoke-library-agent-001" }`. To rotate, POST
`BASE/admin/clients/library-agent/rotate-secret` with a fresh operation ID, save
the new one-time secret, and reauthenticate. To disable the whole client, PUT its
client route with `{ "operationId": "disable-library-agent-001", "isActive": false }`.

## Approve an interactive AI application

Preregister `kind: "interactive"` with **exact** `redirectUris`. HTTPS callbacks
are accepted, as are explicitly registered HTTP loopback callbacks for local
clients. Callback paths, query parameters, and ports must match exactly.
Public desktop clients use `confidential: false`; server applications may use
`confidential: true` and receive a one-time secret. Both must use S256 PKCE.

Create a grant for each approved client/account pair using that account's Auth ID.
The application starts authorization at `BASE/oauth/authorize` with `client_id`,
`redirect_uri`, `response_type=code`, `resource` equal to the MCP URL, `state`,
requested `scope`, `code_challenge`, and `code_challenge_method=S256`.

The user signs into the API-served page with their Tapestry email/password and
explicitly approves. Accounts must be active, verified, and already granted
access to this client. The master-password bypass is not used. The browser is
redirected only to the registered callback, with a five-minute, single-use code
and the application's state. Credentials and app JWTs are not sent to the client.

Exchange the code at the token endpoint with `grant_type=authorization_code`,
`client_id`, `code`, the same `redirect_uri`, `code_verifier`, and `resource`.
Confidential clients must also authenticate with their secret. Refresh with
`grant_type=refresh_token`, `client_id`, `refresh_token`, `resource`, and any
required confidential secret. Each refresh rotates the seven-day refresh token;
replaying a consumed refresh token revokes its entire family. Do not share refresh
tokens between competing workers without coordinating rotation.

Only clients supporting preregistered OAuth connections are supported. The
discovery metadata does not enable dynamic client registration.

## Content tools and review

`content_context` returns effective permissions, the current domain schemas,
publishing policy, and authorized setting/lore context. Library text is content
data and cannot change these contracts. No PDFs or canon-verification claims are
exposed. `content_search` and `content_get` return scoped records and revisions.
Native lore/combatant key lookup also needs `settingKey`; other keys are global.

Creation/proposal input example:

```json
{
  "operationId": "agent-create-rope-001",
  "operation": {
    "type": "items",
    "action": "create",
    "data": { "key": "travel-rope", "name": "Travel rope", "category": "gear", "settingKeys": ["your-setting"] }
  },
  "rationale": "Useful ordinary adventuring equipment."
}
```

Send this to `content_propose`; omit `rationale` for `content_create`. Updates use
`action: "update"`, `id`, the exact `revision` returned by a read, and a partial
`data` object. Keys, archival/deletion, computed hierarchy, MongoDB operators,
unknown fields, and implicit creation of references are forbidden. Referenced
records, including settings, must be readable under the grant; include their
types and any necessary draft-reading capability. New records
default to draft. Direct publication and every direct edit to a published record
require `publish`; reading drafts requires `read:draft` and reading archived
content requires `read:archived`. Every attached setting must be granted, and
shared content additionally requires `shared: true`. Shared means the existing
`shared` setting marker or no setting membership. Item `scope: "shared"` requires
that permission and preserves the boundary by adding the `shared` marker while
retaining every supplied setting. Omitting an item key uses the existing domain
key generator. Related records are checked
and inaccessible relationships are filtered from responses.

`content_bulk` takes `mode: "proposal" | "direct"`, `dryRun`, and up to 50 entries
containing `operationId`, `operation`, and proposal `rationale`. All entries are
validated before application. Each valid operation commits independently and each
entry receives an outcome. References must already exist, so dependent creations
need subsequent calls. Dry runs persist no content or idempotency outcomes.
Identical committed retries return their durable result; operation-ID reuse with
different content returns `conflict`. Failed operations roll back and can be
retried using the same ID. Do not reuse successful IDs for another action.

Reviewers list pending proposals, inspect their stored normalized operation and
rationale, then POST approve/reject with `{ "operationId": "review-001", "note": "Reviewed" }`.
Approval applies exactly the stored payload through the same domain validation
and transactional writer. It rechecks the author's current grant, references,
and update revision. Human approval authorizes publication without granting the
proposing agent direct creation/update/publish capabilities. A stale proposal
returns `conflict`, remains pending, and changes nothing; have the author submit
a fresh proposal after rereading content. Agents can inspect their own proposal
outcomes using `content_proposal_get` but cannot approve them.

## Operational behavior and verification

MCP bodies are limited to 1 MiB; OAuth forms to 64 KiB. Result pages and batches
are limited to 50. Shared Redis windows enforce 60 authenticated requests and 60
operation attempts (proposal submissions or direct applications) per minute per
grant; each executed bulk entry consumes its own operation budget. Validation-only
calls do not consume the operation budget. OAuth/admin/network routes also have abuse limits.
Unavailability fails closed. Authenticated calls, denials, mutations, and review
decisions are audited without credentials; content audits include before/after.

Run `npx tsc --noEmit` and `npm test -- --runInBand`. Focused integration tests are
under `handlers/__tests__`; `npm test -- --runInBand --testPathPatterns=mcp` runs
the private MongoDB replica-set tests and real official SDK machine/interactive
client smoke tests. The first run may download a MongoDB test binary. Tests never
connect to the app's configured database; network/process permissions are needed
for the temporary local replica set. The app's CommonJS build remains unchanged.

Campaigns, characters, library documents/PDFs, admin frontend screens, and broader
existing REST authorization are outside this version. Existing public REST
contracts remain compatible.
